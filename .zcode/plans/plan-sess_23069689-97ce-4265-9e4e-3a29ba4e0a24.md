# backend 多智能体编排改造方案（feature/multi-agent）

## 一、目标与已确认决策

基于 AgentScope 2.0.10 内置的 `TeamPipeline`（leader-worker 模式）实现多智能体编排：

| 决策项 | 结论 |
|---|---|
| 编排模式 | `TeamPipeline`：leader 通过框架自动注册的 `TeamAssign(member, prompt)` 工具委派 member；跨 member 并发、同 member 串行；权限确认（REQUIRE_USER_CONFIRM）由 pipeline 按 reply_id 自动路由回对应 member —— 现有 park/resume 循环无需感知多 Agent |
| 角色划分 | leader=Friday（规划+综合回答）；检索员（医学检索+联网检索+技能）；执行员（Bash/Read/Write/Edit 等内置工具 + workspace） |

**开关设计（全部是本次新增，现有开关一律不动）**：

| 开关 | 在哪 | 谁控制 | 作用 |
|---|---|---|---|
| 「多 Agent」toggle | 前端输入框选项区，与「深度思考」「联网搜索」并排，默认开 | 用户，每轮可切换 | 关 = 走现有单 Agent 老路 |
| `MULTI_AGENT_ENABLED`（默认 true） | 服务端 .env | 部署者 | 总闸：紧急情况一键回退单 Agent，与现有 `agent_tools_enabled` 设计对称 |

技术形态：聊天接口请求体 `ChatRequest` 新增 `multi_agent: bool = True` 字段，前端 toggle 负责 true/false。

（已去掉原方案的 `MULTI_AGENT_WORKERS` 角色清单配置——只有 2 个角色收益太小，且与请求级开关注解耦不开、角色增减必须改代码，属过度设计。）

**关闭时行为**：「多 Agent」toggle 关闭（或服务端总闸关闭）时**不执行任何新代码**——仍由现有 `build_agent()` 创建单个 "Friday" Agent 独立完成整轮对话，行为与现在 main 分支完全一致，现有功能不可能被这次改动影响（零回归）。

**成员裁剪规则（已明确确认）**：
- **web_search 开关只控制检索员是否多挂 `web_search` 这一个工具，不影响检索员的存在**——关闭时检索员仍在，只挂 `medical_rag_search`（恒挂）+ 技能，不挂联网搜索。与现有单 Agent 模式的 MCP 白名单行为一致。
- `agent_tools` 开关（且服务端 `agent_tools_enabled`）控制**执行员**的存在：关→团队缩为 leader+检索员。
- leader 运行时自主决定派谁：简单问题可不委派任何 worker 直接回答。

关键前提（已核实）：`Agent` 与 `TeamPipeline` 都实现 `reply_stream` 协议，`agent.py` 的事件循环对两者通用；worker 中间消息不落库、不回放（TeamPipeline 默认 member 上下文隔离，leader 只见结果摘要），最终落库的仍是 user/assistant 两条消息，`context.py`/`agent_messages.py` 的回放校验**零改动**。

## 二、后端改动（8 个文件）

### 1. `app/config.py` — 新增配置
- `multi_agent_enabled: bool = True`（服务端总开关）

### 2. `app/prompts.py` — 新增三段角色提示词
- `LEADER_TEAM_PROMPT`：追加到 leader 现有 SYSTEM_PROMPT 之后，说明成员分工、何时委派、要求汇总各 worker 结果后作答（简单问题直接答不委派）
- `RESEARCHER_PROMPT`：检索员人设——负责医学文献检索/联网检索/技能调用，返回带来源的结论摘要，不做文件操作
- `EXECUTOR_PROMPT`：执行员人设——只做文件/命令操作，返回执行结果与产物路径
- `TeamMember.description` 用简短中文（leader 路由的唯一依据）

### 3. `app/agent_factory.py` — 参数化 + 新增 build_team()
- `build_agent()` 保持现有签名职责不变，仅抽出可复用参数（name、system_prompt 由调用方拼装）
- 新增 `build_team(...)`：
  - leader：`Agent(name="Friday", SYSTEM_PROMPT + memory_block + LEADER_TEAM_PROMPT, Toolkit(任务工具))`
  - 检索员（团队开启即在）：`Agent(name="检索员", RESEARCHER_PROMPT, 独立 MCPClient(白名单=medical_rag_search[+web_search 按开关]) + SKILL_LOADER)`
  - 执行员（仅 agent_tools 开启时）：`Agent(name="执行员", EXECUTOR_PROMPT, builtin_tools + permission_context 挂其 AgentState)`
  - 每个 Agent 独立 AgentState(session_id=会话id) / 独立 Toolkit / 独立 MCPClient 实例（Toolkit 共享实例会被 Agent 内部改写）
- 历史回放：拿 leader Agent 引用做 `observe(replay_msgs(...))`（worker 每轮全新，`reset_members=True` 默认即如此）

### 4. `app/agent.py` — stream() 加分支
- 解析：`use_team = multi_agent and settings.multi_agent_enabled and not attachments`（带图请求仍走单 Agent 视觉档，多模态不进团队）
- 构建分支：use_team → `build_team(...)`，否则现有 `build_agent(...)`；事件循环、权限 park/resume、演示降级路径全部共用不动
- **事件归属映射**：维护 reply_id → agent 名的映射（从事件流获取；实现时核实 TeamPipeline 事件上的身份字段，若无则在 build 时记录每个 member 的 reply 起点），把当前 agent 名传入翻译器

### 5. `app/agent_events.py` — SSE 事件加 agent 字段
- `ReplyEventTranslator` 增加 agent 名参数/方法：`text`/`thinking`/`tool_call` 三类事件输出 dict 追加 `agent: "Friday"|"检索员"|"执行员"` 字段（旧前端忽略新字段，无破坏）

### 6. `app/schemas.py` + `app/chat.py`
- `ChatRequest` 加 `multi_agent: bool = True`；chat() 透传给 stream()
- 落库：meta.toolCalls 各条目带上 `agent` 字段（随事件流收集）；assistant 消息仍单条（leader 最终回答），meta 加 `multiAgent: true` 标记

### 7. `app/agent_logging.py` — 节点日志带 agent 名（中间件 per-Agent 实例化时传入）

### 8. `backend/ARCHITECTURE.md` — 同步：SSE 协议表加 agent 字段、多 Agent 架构小节、开关说明、成员裁剪规则

## 三、前端改动（2 个文件，轻量）

### 9. `frontend/src/lib/api.ts`
- `ChatRequest` 参数加 `multi_agent`；`StreamEvent` 加 `agent?: string`；Message meta 的 toolCalls 条目类型加 `agent?: string`

### 10. `frontend/src/components/ChatWorkspace.tsx`
- 发送选项区加「多 Agent」toggle（默认开，样式/位置同「深度思考」）
- onEvent 与渲染读 `agent` 字段：tool chip 显示前缀（如「检索员 · 已检索：医学文献库」）；StreamingHint 按当前 agent 显示（「检索员正在检索…」「执行员正在执行…」，Friday 不前缀）；thinking 合流不区分
- 历史渲染：meta.toolCalls 的 agent 前缀同样生效

## 四、风险与实现时需核实的点

1. **TeamPipeline 事件的身份标识**：事件带 reply_id 但需确认是否带 agent 名；若无，用 reply_id 映射（REPLY_START 时建立）。这是 agent 字段的实现关键。
2. **并发 member 同时权限 ASK**：ConfirmHub 每会话只允许一个 pending ask（confirm.py）。TeamPipeline HITL 按 reply_id 路由，但两个 member 同时 ASK 时 stream() 的单 pending 逻辑可能覆盖。核实 pipeline 是否会并发挂起多个 member；若会，confirm.py 的 key 细化到 reply_id 级（预计小改）。
3. **token 成本**：默认开意味着每轮 prompt 增加成员描述 + TeamAssign 工具；leader 对简单问题可不委派，成本可控但非零。文档中明示。
4. **MCPClient 复用**：leader 与检索员不共享 client 实例，各建独立。
