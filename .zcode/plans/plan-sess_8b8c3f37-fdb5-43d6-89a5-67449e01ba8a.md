# Friday Agent 运行时能力评测（OpenJudge + Ragas，当前项目内开发）

## 代码位置决策
评测代码放在**当前项目内**：`backend/scripts/eval_harness/`（延续现有 eval_rag.py 的位置惯例），依赖用独立的 `backend/requirements-eval.txt` 隔离，不进主 requirements。理由：业界 evals-in-repo 主流做法；能进程内直调 `rag.py` 拿检索 contexts（Ragas 必需）；随主项目重构同步演进，避免再出现 eval_agent.py 那样悄悄失效的问题；目录+依赖独立，将来可整体搬走。

## 目标
真实运行 Friday Agent，产出量化评测报告，覆盖 6 个维度：医疗 RAG 检索质量、工具决策、两级记忆、工作区编码任务、安全探针、性能。

## 技术栈
- **OpenJudge**（`py-openjudge`）：Agent 维度——ToolSelectionGrader、RelevanceGrader、HallucinationGrader、MemoryGrader、轨迹质量 + WeightedSumAggregator
- **Ragas**：RAG 维度——faithfulness / answer_relevancy / context_precision / context_recall
- **Judge 模型**：GLM glm-4-flash（已有 Zhipu key，OpenAI 兼容端点，两个框架均支持）
- **程序化断言**（不走 LLM）：安全探针拦截率、Hit@K / MRR（沿用 eval_rag.py 逻辑）、延迟、token 消耗
- 驱动层：httpx 走完整 HTTP SSE 链路（覆盖权限确认 park/resume），RAG 用例进程内直调 `rag.py` 拿 contexts

## 实施步骤

### 1. 依赖准备与冒烟
- `pip install py-openjudge ragas` 写入 `backend/requirements-eval.txt`
- 冒烟验证：GLM 端点各跑一个最小 OpenJudge grader / Ragas metric，确认与 agentscope 2.0.8 无依赖冲突；有冲突则降级（Ragas 换自研 judge，不阻塞整体）

### 2. 搭建评测基座（替换已损坏的 eval_agent.py）
- 新建 `backend/scripts/eval_harness/`：
  - 驱动：注册专用评测用户 → 建会话 → SSE 采集（query、最终回答、thinking、tool_call 序列及参数、各阶段时间戳、meta.toolCalls）
  - 适配重构后的 `AgentService.stream()` 无状态 API
  - 夹具：独立评测账号/会话，跑完清理
- contexts 采集：同 query 直调 `rag.py` 检索函数（可复现）

### 3. 用例集（~50 条，`eval_harness/cases/` 下 JSON 数据文件）
- RAG 检索 20 条（现有 8 条 golden queries 扩充 + 参考答案）
- 工具决策 10 条（该调调了 / 不该调不误调 / coding 任务选对工具）
- 两级记忆 8 条（摘要保真、跨会话长记忆命中、记忆污染检查）
- 工作区编码任务 8 条（建文件/编辑/grep/任务编排 + 权限确认卡三态）
- 安全探针 6 条（deny 路径写入、敏感文件读取、prompt injection）

### 4. 接入 OpenJudge + 5. 接入 Ragas
- mapper 把 harness 采集字段映射到 grader 输入（tool_definitions + 实际 tool_calls）
- Ragas 4 指标跑 RAG 用例集，GLM judge

### 6. 程序化检查与性能
- 拦截率断言、Hit@K/MRR、首 token 延迟、0.05s/事件节流累计影响、token 消耗

### 7. 全量运行 + 报告
- 产出 `backend/logs/eval_report.md` + `eval_report.json`：各维度得分、加权总分、失败用例及复现步骤
- 标注结论来源（LLM judge vs 程序化断言）
